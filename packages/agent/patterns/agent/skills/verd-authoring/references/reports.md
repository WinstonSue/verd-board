# 汇报与讲解场景

仅在当前任务涉及这些场景时读取对应章节；通用表达与证据原则见写作规范。

## 进度汇报

先说总体进展和本次变化，再按模块给状态与证据，最后给下一步。状态可用“已完成、进行中、有风险、卡住、未开始、取消”；它们只是报告词汇，不改变业务状态枚举。已完成必须有证据；全部完成时不必重复铺陈标签。部分成功写清通过数、总数和失败项，不把未执行的检查算作通过。

只汇报有意义的变化；无变化时说明原因，不拼凑进展。下一步写明动作，预计时间有依据才给；用户未要求周期更新时，不因为模板要求定时打扰。

## 阻塞说明

写清四件事：卡在哪一步及证据；已尝试的方法与结果；原因是实测、推断还是未知；需要谁完成什么具体动作。自己能解决的继续处理。确需用户提供凭证、权限或业务决定时，说明为何没有可行尝试，不编造试错记录，也不反复索要已经获得的授权。

## 决策与方案对比

先提出推荐及其依据，再列有意义的备选。按相同维度说明做法、依赖和后续影响、时间或费用成本、风险；不满足已确认硬性条件的选项说明原因。写清关键假设、证据不足和在什么条件下推荐会改变，不编造概率或评分。只有确需用户取舍时才提出明确问题，常规编写和实现选择由 Agent 完成。

## 评审与整合

先给判定和覆盖范围，再逐项列证据、影响、风险与处理建议。整合资料时明确哪些原则保留、哪些因产品能力改写、哪些剔除；把来源观点、当前源码事实和本次判断分开。未检查的范围保持显式。

## 事故与失败复盘

按结论、事实时间线、根因判断、有效处置、失误和后续动作组织。时间线按证据精度记录发现、处置与恢复；推测的根因不得冒充已证实事实。Agent 自身出错时直接说明错误、影响和修正。后续动作写出优先级，有真实负责人或期限才记录。

## 概念与机制讲解

从读者问题进入，先给系统全景，再解释关键路径、边界与失败处理。图必须帮助读者理解关系或变化；箭头写明有意义的动作，图文使用同一术语，不把同一段正文复制到每个节点。静态图足够时不增加交互。

## 路线图与时间安排

写清工作线、真实依赖和里程碑；规划到月就不伪造具体日期。挨得近不代表有依赖，只有确实等待前置结果或交接才连线。基准日期、更新日期和已变化的假设保持可见；不把建议路线写成已承诺交付。

## 验收清单

按读者真实使用流程分组，每步写明输入或前置条件、操作、预期结果，以及异常意味着什么。检查依据来自当前代码、文档或测试。用原生任务列表或表格记录结果与证据，不承诺自动运行或回传；Agent 能执行的检查先执行，只有必须由用户验证的步骤才交给用户。

## 示例：结构与事实分开

短答示例：“当前支持用原生表格比较数据。”若没有安装版本的 schema 证据，则标明待查询 describe，而不是直接承诺折线图。短答无需新建报告。

进度示例：“文档已更新，图表尚未验收。”随后分别附文档变更位置与已执行检查，图表标为进行中；没有预览结果就不能写全部完成。

阻塞示例：“读取来源返回权限错误；重试后结果相同。权限不足是推断，需来源所有者确认访问权限。”不要把没有尝试过的替代路径写成失败。

决策示例：“推荐复用现有文档并补一张架构图，便于维护同一来源；若两组读者需要独立发布，则改为两份文档并引用共享图。”实际成本与风险仍需依据任务填写。

复盘示例：“保存失败时间有日志，恢复时间尚未记录；版本冲突是候选原因，仍需提交回执验证。”不要为完整时间线补造分钟或根因。

图文讲解示例：“正文解释组件职责，独立架构图展示边界，时序图展示失败路径。”三处使用相同的组件名和接口；无需 HTML 或动画播放器。以上为写法示例，不是本项目的实测结果。
